# Learning storage and lifecycle

Decision date: 12 October 2026. This document is the implementation contract for the next backend round. It builds on email identity, friction reports and the Jev classifier from round three.

## Decision

Postgres owns the knowledge. A learning is a typed row with a Markdown body. Private Vercel Blob stores immutable evidence, generated Markdown files and downloadable snapshots. Agents can search the rows or navigate a file tree. Both expose the same learning ids and lifecycle. Only writes through Hive change the source of truth.

## Source of truth and evidence

Keep the existing learning id, team, member, agent source, source session, kind, repo, area, paths, tags, confidence and timestamps. Add lifecycle, `verify_after` and a monotonically increasing version. Use the existing kinds, including insight and friction. Environment is an area and a freshness policy, not another incompatible kind.

Add `learning_versions` with team id, learning id, revision, author, timestamp, the complete redacted content and a readable diff from the preceding revision. Changes to bodies, titles, metadata or lifecycle create a version in the same transaction. Push counts and vote counters remain observations; a duplicate does not replace the body merely because it is longer. A correction becomes a new learning with an edge. Explicit edits to an existing learning preserve its identity and record a version.

Each accepted push adds an evidence record, including merged duplicates. Keep the submitted payload after secret redaction, plus any supplied session excerpt and diff, in an immutable private object. Record its content hash, byte count, object key, push id, learning id and team id in Postgres. Never upload unredacted input. Raw here means the submitted evidence, not an exemption from redaction. Queue the redacted payload transactionally until upload succeeds; then retain the pointer and digest. A retry reuses the evidence id and verifies the digest. Legacy pushes have no invented raw evidence.

Choose Vercel Blob because Hive already deploys on Vercel. Use a private store, server-side access and `BLOB_READ_WRITE_TOKEN`. Do not publish team memory at public blob URLs. Wrap storage behind a small interface for tests and a future S3 adapter. Missing credentials leave evidence and tree work pending and return a clear storage-unavailable result for blob tools. They do not fail an otherwise durable push or pretend that an upload succeeded.

Blobs alone cannot enforce team references, version transitions, votes or atomic supersession. Searching every file also makes retrieval cost grow with the whole hive. Rows alone can hold the small canonical Markdown body, but raw excerpts and diffs are bulky append-only evidence. Keeping those objects outside the frequently searched table avoids coupling evidence growth to row scans and database backups. PostgreSQL remains necessary to index and authorize every object.

## File-system view

Expose a materialised tree for each team:

```text
INDEX.md
repos/<owner>/<name>/<area>/<slug>-<learning-id>.md
notes/<area>/<slug>-<learning-id>.md
topics/<tag>.md
people/<member-id>.md
friction/<area>.md
```

Paths are relative, normalized and generated by the server. The learning id prevents title collisions. Reject absolute paths, traversal, backslashes and control characters. Member pages use stable ids, not email addresses. Repo-less learnings go under notes. Topic pages group normalized tags and link to canonical files. Person and friction pages are indexes of recorded observations, not inferred personal profiles.

Every canonical file includes id, lifecycle, author agent, repo, tags, source session, revision, last update, verification horizon and supersession pointers, followed by Markdown. Historical cells stay readable with their replacement pointer. Index and topic pages distinguish current facts from history; they never silently present superseded guidance as current.

On each transaction, enqueue the affected learning ids and team revision. Regenerate the affected canonical files and dependent indexes after commit. Store immutable content-addressed blobs and a Postgres manifest mapping team and logical path to object key, hash and revision. Publish a complete manifest revision only after all its objects exist. Serialize publication per team and reject stale generation work so an older worker cannot replace a newer manifest. Preserve the previous published revision when storage fails. A durable dirty flag or outbox lets the next request or a rebuild job retry. An explicit rebuild command reconciles all files from rows, including removed and renamed paths.

`hive_browse({path})` returns immediate children, their type and the published revision. `hive_read({path})` returns the file body and its revision. Both authorize through the manifest and authenticated team, never through a user-supplied blob key. A dirty tree is rebuilt before reading where possible; otherwise return a clear stale or unavailable status.

`hive_snapshot({})` returns a short-lived URL for a `.tar.gz` containing a consistent published manifest revision and its files. Generate the archive on demand and cache it by revision. Use an authenticated, expiring application download route backed by a random hashed bearer token scoped to the team, requester and snapshot; recheck that the requester is still a member. Treat the download URL as a credential. Archive entries have relative safe paths, ordinary files and no links. An agent can unpack and grep the archive locally. Local edits have no effect; corrections go through `hive_push`.

## Supersession, conflict decisions and decay

Lifecycle values are fresh, confirmed, superseded, outdated and retracted. Fresh means accepted but not corroborated. Independent positive feedback or repeated corroboration can confirm a current cell. Outdated marks a fact that should no longer guide work. Retracted records withdrawal. Superseded means a known newer cell replaces the old claim. Neither time passage nor a duplicate push revives a historical cell.

Store directed `learning_supersessions` edges from an older id to a newer id, scoped by team at both foreign keys. Status is candidate, accepted or rejected. Keep the relation (update or contradiction), classifier confidence, decision reason, deciding member and timestamps. Reject self-links, cycles, cross-team ids and a second accepted replacement for the same old cell. If a cell already has a successor, ask the pusher to supersede the current endpoint instead. Resolve edges and update lifecycle in one transaction under a team lock.

Before duplicate merging, find a bounded set of similar current cells in the same team and repo. Use vector similarity and a normalized-title fallback. Ask Jev whether each pair says the same thing, updates a previous fact, contradicts it, or is unrelated. Similarity is candidate generation, never proof of agreement. Classifier outage or uncertainty must not merge differing bodies or silently retire a fact. Exact normalized content can still dedupe without a model. Repeated friction reports retain their existing observation accounting.

`hive_push({supersedes: "lrn_..."})` remains an explicit replacement instruction by an authenticated team member. Validate the target before committing. Other update or contradiction candidates resolve automatically. The current policy is in [SPEC.md](SPEC.md#automatic-conflict-decisions-13-october-2026): typed Jev questions, then one Sonnet structured decision, with confidence floors and automatic retry when neither model can decide.

The `conflict_decisions` ledger records linked cells, model judgments and outcomes. Admins can reverse an outcome through MCP or Slack while the recorded state still matches. Round C removes the Decisions and tree pages; Team retains archive export and agents retain browse/read/snapshot tools.

`verify_after` is an absolute ISO timestamp supplied on push or derived at creation. Default horizons: environment facts 14 days; snippets and incidents 30 days; gotchas and friction 45 days; learning and insight 90 days; decisions 180 days. Version, dependency and URL tags shorten the horizon to at most 30 days. Explicit horizons take precedence. A past horizon yields `verifyBeforeUse: true` without deleting history or asserting that the fact is false. A duplicate does not extend the horizon. Reverification is an explicit edit with new evidence and a new horizon.

## Retrieval and answers

Keep hybrid vector, full-text, recency and votes. Default search, ask and recent exclude superseded, outdated and retracted cells, net-negative cells (`down >= 2` and `down > up`), and cells with a current evidenced contradicted outcome newer than their latest current useful outcome. With no useful outcome, a current evidenced contradiction excludes immediately. Apply filters before candidate limits. All three tools accept `include_history: true`; direct ID reads retain hidden cells. Withdrawal restores the prior contribution and recomputes eligibility immediately.

Use audience-scoped current feedback and receipt timestamps. Supported contradictions stamp the receipt even when evidence is cited inline. Privacy redaction preserves the stamp. Each current useful/up contribution is +1, and each contradicted/down contribution is -1. Multiply each by `2^(-ageDays / 90)`, then use `votes = clamp(0.5 + weightedNetVotes / 6, -0.5, 1.5)`. Three fresh net useful outcomes double the neutral votes term. Outcomes already map to votes and never count twice. Repeat pushes add no feedback weight. Text/vector weights remain dominant. Organisation publication votes and outcome stamps never change the personal original or another organisation. The read model adds `unhelpfulLabel` ("Marked unhelpful by N"), `retrievalExcluded` and `feedbackStanding` for the comb. Apply lifecycle and verification weights to current candidates: confirmed has full weight, fresh has 0.95, and overdue verification multiplies by 0.7. Return these signals so ranking is explainable.

Before synthesis, Jev reranks a bounded shortlist for relevance to the question. Pass each candidate's counts, outcome summary, latest outcome timestamps and lifecycle. Use a separate judgment per candidate, batched in one request. Preserve deterministic hybrid ordering on failure. Classifier relevance changes ranking, never team scope or lifecycle eligibility.

When `include_history: true`, fetch accepted predecessor chains within the same team. Default answers omit historical chain citations. Supply chain ids, titles and dates as historical context, clearly separated from current bodies. Append deterministic citation context with the as-of date, replacement links and overdue verification warnings to both synthesized and extractive answers. The model cannot be trusted to mention every lifecycle warning. Chain expansion is bounded and signals truncation. Validate citations against the current hits and their authorized ancestors; historical citations explain what changed, not what to execute now.

## Topics

Keep normalized tags as the grouping primitive. Extract service, tool and repo-area candidates from the submitted text and use Jev to select supported entities. Reuse the round-three classifier where possible. This is selection from evidence, not free-form invention. Regenerate topic pages when tags change. Keep explicit pusher tags. No graph database, ontology or relationship crawler is required.

## Tool and dashboard contract

Existing tools retain their names. Push gains `supersedes`, `verify_after`, and optional redacted `evidence` with session excerpt and diff. Search gains `include_history`. Responses add lifecycle, verification deadline/marker, version and replacement pointers. Add `hive_browse`, `hive_read`, and `hive_snapshot`. Dashboard APIs share the same authenticated services for decision log and reversal, version reads and the file tree. No route accepts a team id from a caller.

## Out of scope

No writable agent filesystem, arbitrary sandbox execution, autonomous edits to repositories, full session ingestion, branch-aware truth model, heavy knowledge graph, external-document crawler or retroactive reconstruction of missing evidence. No automatic deletion from age. No public blob sharing. Storage retention and organization-wide retention controls need a separate policy; retraction removes current guidance but preserves authorized history. Better Auth is a later round and must keep these team-scoped contracts intact.

## Capture and outcome contract, 13 October 2026

The current tool contract is [Observation capture and outcome feedback](SPEC.md#observation-capture-and-outcome-feedback-13-october-2026). Agents submit observation, optional evidence and runtime context; Hive owns titles, classification, friction metadata, verification and conflict decisions. Old explicit fields remain optional overrides. Capture rules and sensitive-data filtering precede title generation. Unknown blocking impact and unmeasured cost remain null. Retries use content, repository, session and actor identity to avoid duplicate observation accounting.

`hive_correct` creates a revision-checked edit or audited retraction. Evidence remains in the private evidence queue. Outcome reports attach a concrete cited result to the cell used. Jev's pure policy classifies useful, contradicted, stale or inconclusive, then code uses the existing vote and lifecycle rules. Inconclusive is audit-only. One member has one contribution per cell across agents and credentials. Receipt withdrawal restores the actor's preceding contribution and recomputes standing without undoing other members' feedback.

Postgres stores feedback receipts with actor, evidence, classification, model judgment and before/after state. Current feedback points at its actor-bound receipt. The cell history shows these results beside content revisions. Capture-rule scans inspect receipt evidence; redaction removes protected text while preserving numeric and lifecycle audit. Held outcomes are owner-only and have no vote. Reads never create feedback.

Migrations 0022 and 0023 preserve existing data, relax blocked nullability, add capture retry keys and store audited outcome receipts. Rollbacks refuse new capture or outcome history. They run at the landing commit through the repository migration runner before dependent code is pushed.
